# Working on demo-news-feed

Read README.md, docs/product-brief.md, docs/decisions.md,
docs/baseline-spec.md, docs/implementation-brief.md, and docs/acceptance.md first.
Read docs/exercises.md to understand what must remain outside the baseline.

## Assignment

Build the agreed basic application as a stable starting point for independent
practice and ExecDesk exercises. This pack is a delegation context, not evidence
that its proposals have been approved or the app has been implemented.

Check the decision register before coding. If a material choice remains open,
prepare a concrete recommendation with alternatives and ask Gabriel. Continue
independent preparation while waiting. Do not treat silence or a recommendation
label as approval. Existing explicit approvals need not be requested again.

Proceed through routine implementation, documentation, and proportionate checks
within the agreed scope. Use maintainable, focused files. Stop for consequential
product, UX/design, architecture, dependency, privacy, or data choices; present
what is known, viable options, and your recommendation. Do not invent ceremony or
ask permission for routine reversible edits already authorized by the task.

## Boundaries

- Baseline work is confined to this repository. No ExecDesk or sibling-repo edits.
- docs/exercises.md contains optional future exercises, not implementation work.
- Scope/design decisions and final acceptance remain Gabriel's unless explicitly
  delegated. Do not convert your own suggestions into accepted decisions.
- Do not commit, push, merge, tag a release, publish/deploy, change repository
  visibility, or create external issues/PRs unless Gabriel explicitly authorizes
  that action for this project. Prior authority in another project does not apply.
- Do not use paid services, acquire credentials, start paid model tests, or
  introduce external runtime services without explicit authorization.
- Do not discard unrelated local changes or reset data as incidental cleanup.
- A fictional author selector is not authentication; never describe it as such.

## Handoff

Before claiming completion, report what exists, how to run/reset it, checks
actually performed, known limitations, and any unresolved decisions. Identify
changes from the initially approved scope. Leave a reviewable working tree; final
acceptance and delivery remain separate from implementation completion.

## Preserve the baseline during exercises

Before changing files for an exercise, inspect the current branch and working tree.
Use a separate exercise branch; if the checkout is on main, create or switch to an
exercise branch before editing. Preserve unrelated changes. Do not merge exercise
solutions into main automatically. A completed exercise may remain uncommitted or
unmerged. Baseline maintenance and promotion of exercise work require explicit
authorization; commit/push authority is still governed by the boundaries above.
